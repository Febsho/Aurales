# Aurales browser platform audit

## Existing architecture

Aurales is already one React 19 + TypeScript + Vite application. `src/App.tsx` owns the routed shell and profile bootstrap; `src/components/Layout.tsx`, the page components, Zustand stores in `src/stores/`, metadata/addon services in `src/services/`, and localStorage profile contracts are reusable. `src/services/sync/auralesSync.ts`, `syncBatch.ts`, `outbox.ts`, and `encryptedVault.ts` implement the current sync contracts and should remain the source of truth.

Playback selection is in `src/components/StreamSelector.tsx`; the default web fallback is `src/components/InAppPlayer.tsx`; native playback is `src/components/NativeMpvPlayer.tsx` backed by Rust IPC in `src-tauri/src/commands.rs`, `libmpv_player.rs`, and the native process/platform modules. Rust owns image caching, SQLite cache, stream probing/scoring, metadata normalization/resolution, anime helpers, subtitle extraction, server integrations, secure login, Discord, and OS auth flows. Native mpv provides broad codec support, track/chapter discovery, embedded subtitle access, native window integration, and player telemetry that HTML video does not expose equivalently.

## Browser blockers found

- Direct `@tauri-apps/api/core`, `event`, and `window` imports occur across player, settings, addon/catalog, metadata, provider, cache, sync, and integration services. These invoke Rust commands such as `resolve_metadata`, `stream_probe`, `cache_*`, `image_cache_*`, `launch_embedded_mpv`, `mpv_command`, and native OAuth/open-window commands.
- `src/components/NativeMpvPlayer.tsx` is imported from `StreamSelector.tsx` and watch-together code and assumes mpv IPC/events, native window sizing, `convertFileSrc`, and filesystem-backed subtitles. It must only be selected on Tauri.
- `src/components/InAppPlayer.tsx` already uses `<video>` and now loads HLS.js on demand for MSE browsers, routes native HLS to the browser engine, applies existing audio-language preferences to HLS tracks, and reports CORS/expiry/codec failure causes. It still imports Tauri IPC for desktop subtitle fallback. The optional Rust media worker provides authenticated stream ranking plus an allowlisted signed-session proxy for direct media and HLS playlists, rewriting HTTP(S) playlist references into child sessions; it does not transform media.
- `src/services/imageCache.ts` calls Rust image-cache IPC and uses `convertFileSrc`; browser mode should keep using origin URLs and browser HTTP caching. `src/main.tsx` currently waits briefly for Rust cache setup before mount.
- Simkl AUTH V2 now branches by platform in `src/services/simkl/auth.ts`: desktop retains the Rust loopback callback and Rust token/account requests; web uses a registered same-origin callback (`/auth/simkl/callback`), validates state and issuer, and exchanges/refreshes/fetches account data from the public API. The public-client flow uses no client secret. Simkl token and account endpoints returned CORS preflight responses permitting an arbitrary origin and the required POST/GET headers in a live OPTIONS check on 2026-10-18; a real authorized browser exchange still needs an installed client and user approval.
- Stores predominantly persist directly to localStorage; that contract works for same-origin browser/PWA storage. The browser now adapts the existing cache API to IndexedDB with the same cache keys/categories/expiry fields, including normalized app metadata. Aurales Sync preserves its payload contract and uses its existing fetch transport; browser password persistence remains intentionally disabled, with an explicit vault-unlock flow that downloads remote state before any upload.
- The Rust stream-ranking algorithm and media-probe range-header interpretation are in `packages/aurales-domain`; desktop IPC and the standalone `media-worker` reuse them. The worker exposes authenticated health/capabilities, ranking, and allowlisted stream-probe routes with exact-origin CORS, bounded bodies/concurrency, and a per-device key. Its optional HTTPS proxy supports expiring signed direct-media and HLS child sessions with Range passthrough. When FFmpeg is explicitly configured, it can download allowlisted direct files for stream-copy MP4 remux, video-copy/AAC audio conversion, or H.264/AAC conversion.
- `vite.config.ts` reads `src-tauri/tauri.conf.json` and is the desktop/dev build. This increment adds `vite.web.config.ts`, `build:web`, and browser shims so the browser output does not need the Tauri package implementations or native player implementation.

## Current browser build and deployment

Run `npm run dev:web` for the browser-targeted dev server, `npm run build:web` to create `dist-web/`, or `npm run preview:web` to preview that browser build locally. Run the local media test with `npx playwright install chromium` once, then `npm run test:browser`; Vitest excludes this separate Playwright suite. Deploy the contents of `dist-web/` to any HTTPS static host and configure history fallback so unknown paths serve `/index.html` with status 200. A checked-in production Nginx example is available at `deploy/nginx/aurales-web.conf`; optional-worker systemd and Caddy examples are in `deploy/systemd/aurales-media-worker.service` and `deploy/caddy/aurales-media-worker.Caddyfile`. For Nginx, use `try_files $uri $uri/ /index.html;` within the site location. Serve `.webmanifest` as `application/manifest+json` (or `application/manifest+json; charset=utf-8`), enable gzip/Brotli for JS/CSS, and use HTTPS for PWA and secure-context browser APIs. `VITE_SIMKL_V2_CLIENT_ID` is optional and supplies a public Simkl AUTH V2 client ID. For browser Simkl sign-in, register the exact HTTPS callback URI and set it as `VITE_SIMKL_WEB_REDIRECT_URI` (default: `<app-origin>/auth/simkl/callback`); it must remain same-origin with the deployed app. `VITE_SIMKL_REDIRECT_URI` remains the desktop loopback redirect. For browser MDBList OAuth, set public `VITE_MDBLIST_CLIENT_ID`, register `<app-origin>/auth/mdblist/callback` in that MDBList client, and optionally override the redirect with same-origin `VITE_MDBLIST_WEB_REDIRECT_URI`; the default uses the deployed origin and callback path. When the optional worker is configured, MDBList account and OAuth calls use its authenticated, fixed-origin provider relay to avoid browser CORS restrictions; otherwise requests use direct browser HTTPS and depend on provider CORS. Browser AniList sign-in uses the provider’s implicit grant and auth-pin redirect so no client secret enters JavaScript: register `https://anilist.co/api/v2/oauth/pin` in a public AniList client, set optional `VITE_ANILIST_WEB_CLIENT_ID` or save that public client ID in Settings, then copy the token AniList displays into the existing token field. See the [AniList implicit grant guide](https://docs.anilist.co/guide/auth/implicit/). Desktop AniList authorization keeps its Rust-only client-secret exchange. The optional authenticated Rust worker configuration and exact deployment steps are in [docs/media-worker.md](docs/media-worker.md); the browser stores the per-device worker key outside Aurales Sync. Never put a provider client secret or worker key in a `VITE_` variable. Users configure their other provider keys/addons in Aurales settings, and those user values stay in that browser's localStorage.

Direct playback depends on browser codec/container support and provider CORS/Range behavior. Safari/iOS has different HLS and autoplay policies; Chromium and Firefox generally need MSE for HLS. HTML video track APIs vary, embedded ASS/PGS subtitles and many audio codecs are unsupported, and HDR/Dolby Vision support is device/browser specific. The optional worker supports allowlisted Range-aware direct files and rewrites HLS playlist URLs, but cannot solve DRM requirements that depend on provider-specific HTTP headers. FFmpeg conversion works only for direct media files from allowlisted hosts, requires complete source download and private temporary storage, and cannot guarantee HDR/Dolby Vision preservation or provider URL freshness. PiP and AirPlay controls are feature-gated by the active video element APIs; their behavior still needs physical-device validation. Chromecast remains unavailable because Aurales has no verified Chromecast receiver integration.
